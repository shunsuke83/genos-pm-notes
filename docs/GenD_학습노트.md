## 1. 플랫폼 한 장 요약

| 항목 | 내용 | 근거 |
|---|---|---|
| 정의 | "Trino 기반 Federation SQL 위에 AI Text-to-SQL, 데이터 거버넌스, 데이터 품질을 통합한 AI-Native Data Intelligence Platform" | [확인] GenD 가이드 첫 페이지 |
| 한 줄 설명(PM용) | 여러 DB·데이터 레이크·문서를 한 곳에서 SQL과 자연어로 조회하고, 누가 어떤 데이터를 볼 수 있는지(권한·PII·보안 등급)와 데이터가 믿을 만한지(품질·계보)를 관리하는 데이터 플랫폼 | 정리 |

| 데이터 흐름 B-2 (질문→문서 근거 답변) | 질문 → Weaviate 벡터 검색(열람 등급을 server-side where로 강제) → LLM(AI 모델 제공자·바인딩) → 답변 + 출처(document_id·chunk_index, v1.4+) | [확인] AI 인텔리전스, 보안 등급 관리, 릴리스 v1.4.0 |
| 외부 입구 | REST `/api/v1/...`(Bearer JWT, 활성 워크스페이스 스코프) · MCP 서버 `POST /mcp`(JSON-RPC 2.0 Streamable HTTP, 도구 39개 실측 2026-08-21) · JDBC(외부 BI 도구가 Trino에 접속) · CLI `gend`(데이터셋·파일·인증) | [확인] 범위와 연동 표면 §2, API 레퍼런스, 공통 핀 |
| 버전 | 최신 릴리스 v1.4.4(2026-10-25), v1.4.5 준비 중. 지원 정책: 최신 minor 전체 지원, N-2 보안 백포트, minor 순차 업그레이드 | [확인] 릴리스 노트, 지원 정책 |
| 제약·주의 | 온프렘(v1.4.2~v1.4.4)은 실시간 모델 서빙(KServe) 미포함 · Velero 백업 미배포(2026-08-07 실측, CronJob 백업만) · 등급 미지정 데이터는 CONFIDENTIAL로 판정(fail-closed) · 인텔리전스 메뉴 대부분 "준비 중" · GenOS 전용 연동 규격 "미정" | [확인] 각 문서 |

**PM이 꼭 기억할 사실 10가지**

1. GenD는 **데이터 평면**이다. 고객이 "챗봇"을 원하면 GenOS(또는 MCP로 GenD를 부르는 다른 앱)가 답이고, "여러 DB를 한 번에 조회·통제"를 원하면 GenD가 답이다. [확인]
2. 접근 통제는 **2축 직교 모델**이다. 격리 축(워크스페이스, fail-closed) × 권한 축(역할·그룹·grant), 그 뒤에 행/열 ABAC, AI 경로에는 열람 등급(clearance)이 따로 붙는다. 카탈로그에 보여도 테이블 SELECT grant가 없으면 403(deny-by-default). [확인]
3. AI가 참조하는 범위는 **보안 등급(PUBLIC / CONFIDENTIAL / TOP_SECRET)**과 호출자 열람 등급으로 결정되며, 플랫폼 admin이라고 자동으로 열람되지 않는다. 등급 변경은 재로그인해야 반영된다. [확인]
4. Text-to-SQL 경로는 **SqlGuard가 조회문(SELECT·WITH) 한 문장만 통과**시킨다(구문 트리 판정, v1.4.2+). 다만 AI 에이전트 채팅은 별도 **Tier 안전장치**로 움직인다 — Tier 1(조회, 자동 실행) / Tier 2(마트 생성·용어 생성 등 쓰기, 확인 카드 승인 후 **실제 실행**) / Tier 3(커넥터 생성·파이프라인 실행·데이터 삭제, 계획만 안내). "AI는 읽기만 한다"고 단정하면 틀린다. [확인]
5. 설치는 **Kubernetes 전제**다. 온프렘은 kubeadm 3노드(Rook-Ceph, Harbor), 노드당 8코어/32GB 이상, 40+ 워크로드. 에어갭 번들(v1.1.0+)이 있으나 설치 스크립트는 번들이 아니라 소스 트리에 있어 매체에 둘 다 실어야 한다. [확인]
6. **온프렘 실시간 모델 서빙은 미제공**(KServe 미포함, v1.4.2~v1.4.4). 모델 등록·실험·배치 예측은 된다. [확인]
7. 백업은 야간 CronJob(PostgreSQL·OpenSearch·Weaviate) + AES-256 암호화인데 **복호화 키(Secret gend-backup-encrypt-key)를 잃으면 백업도 잃는다**. Velero는 배포돼 있지 않다. [확인]
8. 릴리스가 잦다. v1.0.0(2026-08-04)에서 v1.4.4(2026-10-25)까지 약 3개월. minor는 건너뛸 수 없고 순차 업그레이드해야 한다(DB 마이그레이션 누적). [확인]
9. GenOS와 **같은 클러스터·같은 GPU 노드에 동거**하는 온프렘 사업 모델이 있고, 그로 인한 충돌(쿼터·PDB·알람·GPU 원장 불일치)이 실측·문서화돼 있다. ADR은 "분리를 기본값"으로 제안한다. [확인, ADR 제안]
10. 데이터 품질 점수는 **4축 가중 평균**(완전성 0.3 · 고유성 0.25 · 신선도 0.2 · 일관성 0.25, 0~100점)이다. "데이터 품질 몇 점"이라는 요구는 이 정의로 바꿔서 합의한다. [확인]

## 2. GenOS와 GenD 비교 (PM 관점)

| 비교 항목 | GenOS | GenD | PM 시사점 |
|---|---|---|---|
| 역할 | AI 앱·에이전트 평면: 모델 서빙, 워크플로우(Flowise), 채팅 앱, MCP·A2A, 크레딧 | 데이터 평면: 연합 SQL, 적재 파이프라인, 거버넌스, 품질·계보, NL2SQL, MCP 서버 | 요구가 "서비스"인지 "데이터"인지로 제품을 가른다 |
| 사용자 인증 | 자체 IAM(사용자·관리 그룹·정책·역할), 비밀번호 로그인(실환경) | Keycloak(OIDC, PKCE), Google SSO(운영), 역할 admin/analyst/viewer | GenD는 SSO가 기본이고 GenOS는 [확인 필요] — 통합 사업이면 계정 체계 통일 과제 |
| 테넌트 분리 | 워크스페이스(v1.9.0) + 관리 그룹 | 워크스페이스(Keycloak 그룹 /tenants/<slug>) + 부서(ResourceGroup) | 두 제품의 워크스페이스는 별개 개념, 매핑 설계 필요 [확인 필요] |
| 문서·벡터 | 벡터 DB(Weaviate 기반 노드), 전처리기(Doc Parser), AI 드라이브 | 파이프라인 스튜디오(파싱·청킹·임베딩), Weaviate 컬렉션, 그래프 스토어 | 둘 다 Weaviate를 쓰지만 인스턴스·컬렉션은 별개 [추정]. 문서를 어느 쪽에 적재할지 결정 필요 |
| 정형 데이터 | 데이터 분석 앱(데이터 소스) | Trino 연합 SQL, 커넥터(PostgreSQL·MySQL·SQL Server·Oracle·Hive·Iceberg·Delta·MongoDB·Kafka) | DB 조회 요구는 GenD가 본진 |
| AI 모델 | 자체 서빙(vLLM·Triton·SGLang)+외부 API, 서비스 라우터 | AI 모델 제공자 등록(외부 LLM/임베딩 엔드포인트) — GenOS 서비스 라우터를 공급자로 등록 가능 | GenD는 모델을 띄우지 않고 GenOS 서빙을 쓰는 구성이 문서화됨 |
| 에이전트 연동 | MCP 도구·서버 만들기, 에이전트 게이트웨이, A2A | MCP 서버 내장(/mcp), 워크스페이스 MCP 도구·마켓플레이스, MCP 게이트웨이(관리 콘솔) | GenOS 에이전트가 GenD MCP 도구를 호출하는 경로가 튜토리얼에 있음 |
| 감사·보안 | 감사 로그(v1.9.4), 가드레일, 보안등급(문서 레벨 0~10) | 감사 로그(OpenSearch, 전체 API 요청), PII(Presidio), 보안 등급 3단계, 행/열 ABAC, NetworkPolicy default-deny·Linkerd mTLS(ADR) | 두 제품의 "보안등급" 체계가 다르다(10단계 vs 3단계) |
| 비용 통제 | 크레딧·월 예산·단가표 | 비용 대시보드(쿼리 비용, 사용자/팀별), AI 모델 사용량, 저장소·GPU 쿼터 | 과금·라이선스 단위는 둘 다 [확인 필요] |
| 릴리스 주기 | 약 2주(v1.4→v1.9.6) | 패치 주 1회 안팎, minor 월 1회 안팎(v1.0.0 8/4 → v1.4.4 10/25) | 둘 다 변경 관리 합의가 필수 |

## 3. GenOS 동거(통합 설치)에서 알아야 할 것

문서가 실측으로 적어 둔 내용이라 제안·견적에 바로 영향을 준다.

| 사실 | 내용 | 근거·상태 |
|---|---|---|
| 동거 사업 모델 | "온프렘 통합 AI 플랫폼 사업에서 GenD는 GenOS와 같은 클러스터, 같은 GPU 노드를 쓴다." MLOps 작업은 주간 배치 추론·야간 배치 학습으로 협의됨 | [확인] ADR-0066 배경 (상태: 제안, 2026-09-06) |
| 분리가 기본값 | 네임스페이스 분리만으로는 부족하다는 prod 실측 4건: ① 남의 CPU 쿼터 고갈 → PDB → 노드 drain 불가 → 업그레이드 실패 ② 알람 채널 충돌 ③ 클라우드 vCPU 쿼터 공유 ④ falco·Prometheus 등 클러스터당 하나. 권고: 전용 노드풀+taint, 가능하면 클러스터 분리 | [확인] ADR-0048 (제안, 2026-08-16) |
| GPU 공유 | GenD는 GPU 스택을 설치하지 않고 사이트 gpu-operator MIG 통째 모드를 그대로 씀(ADR-005의 KAI·HAMi는 코드 0줄, 인용 주의). MIG 프로파일 이름이 테넌트 경계. **GenOS GPU 할당량(원장)은 DB 값이라 GenD 소비를 보지 못해 GenOS 서빙이 Pending에 빠질 수 있음** → 2단계는 GenOS 이슈 #20590(원장이 GenOS 밖 사용량 반영) 반입이 전제 | [확인] ADR-0066 (제안) |
| 파드 수 한도 | kubelet 기본 max-pods 110은 GenOS 동거 단일 노드에서 넘침. 여유 70 이상, 동거면 250 권고 | [확인] 온프렘 설치 §1 |
| 패키지 인덱스 | GenOS가 띄운 사내 pypiserver(llmops-pypi-server)를 GenD 코드스페이스·코드 노드가 공유 가능. 패키지는 GenOS 인덱스에 wheel로 올라가 있어야 함 | [확인] ADR-0071, 패키지 인덱스 |
| 임베딩 공급자 | 설치 §6.6: 사이트 임베딩 공급자로 GenOS 서비스 라우터의 게이트웨이 주소(`/api/gateway/service-router/<endpoint>/v1`)를 등록하고 임베딩 use-case를 전사 바인딩. 용어집·계보·스키마 그래프의 선행 조건 | [확인] 온프렘 설치 §6.6 |
| MCP 연동 | GenOS 에이전트(MCP 노드)가 GenD `/mcp`를 호출. 호출자 신원·워크스페이스·열람 등급이 화면과 똑같이 적용. 정적 Bearer 헤더만 지원하는 클라이언트를 위해 트래킹 키 직접 수용(ADR-0058)·워크스페이스 공용 키(ADR-0060) | [확인] 온보딩 여정 §5, ADR-0057~0061 |
| 알림 | 알림 대상 종류에 GenOS 포함(Webhook·Slack·이메일·GenOS·텔레그램). 폐쇄망은 "GenOS 플랫폼 내부 알림 UI만 사용" 구성 가능 | [확인] 알림 egress 가드(ADR-0088) |
| 전용 연동 규격 | "GenOS 연동은 미정. 다만 MCP/REST는 표준 프로토콜이라 별도 규격 없이 호출 가능" | [확인] 범위와 연동 표면 (2026-08-21) |

**PM 판단:** 통합 사업 제안서에는 (a) 클러스터·노드풀 분리 여부와 GPU 카드 배분표(MIG 프로파일별), (b) 계정 체계(Keycloak SSO vs GenOS 로그인), (c) 문서를 어느 제품에 적재하고 누가 벡터를 소유하는지, (d) GenOS 원장과 GenD GPU 사용의 불일치 리스크, (e) 두 제품의 업그레이드 주기 조율을 가정으로 적어야 한다. 전부 개발·인프라팀 확인이 필요하다.

## 7. 학습 주제별 상세 (10회 틀에 매핑)

### 7-1. 데이터 수집과 지식 관리 (GenOS 3회차 대응)

- 입구 4종: DB 커넥터(Trino 카탈로그로 연합), 파일·문서 수집(/ingestion), 파이프라인 스튜디오(소스→처리→스케줄→확인 위저드, v1.4+), CSV/Excel→Iceberg 적재(.xls 거부, 헤더보다 많은 칸은 경고 없이 버려짐 v1.4.4) [확인]
- 문서 형식: PDF, DOCX, **HWP/HWPX**, 이미지, 오디오 등 [확인] 형식 목록 / 품질은 [확인 필요]
- 적재 상태는 파일별 PG · Vec · Graph 뱃지로 본다. "적재는 됐는데 검색 0건"은 전용 진단 문서(무서명 벡터 청크)가 있다 [확인]
- 컬렉션 이름 규칙: 스튜디오에 snake_case로 적으면 Weaviate에는 PascalCase로 저장·검색된다(`yahoo_chunks` → `YahooChunks`). 검색·MCP가 기준으로 삼는 이름은 변환 후 이름 [확인]
- 스키마 동기화: 구조 먼저, 임베딩은 명시적으로(ADR-0074). 임베딩 공급자가 없으면 `skipped_no_provider`로 벡터 없이 동기화됨 → 용어집·계보·그래프가 비어 보일 수 있음 [확인] 설치 §6.6
- Medallion: Bronze(원천 그대로) / Silver(정제·PII 마스킹) / Gold(마트) [확인]
- 데이터 마트: 마트 빌더, ws-admin 위임(ADR-0078). 학습 데이터셋: 워크스페이스 스키마(iceberg.ws_<slug>) 소유, Iceberg 스냅샷으로 버전 고정(ADR-0027), 저장소 쿼터(ADR-0039) [확인]

**실무 사례 — 적재는 됐는데 AI 검색이 0건**
- 증상: 파이프라인 실행 성공, 벡터 뱃지 초록인데 AI 어시스턴트 검색 결과 없음
- 가능한 원인: 컬렉션 이름 불일치(snake→Pascal) / 문서 보안 등급 > 호출자 열람 등급(결과가 조용히 필터링) / 다른 워크스페이스 컬렉션 / 임베딩 공급자 미바인딩 / 무서명 청크
- 확인: 데이터 관측 › 벡터 인덱스의 컬렉션 이름·문서 수, 내 열람 등급(워크스페이스 설정), 활성 워크스페이스, AI 모델 바인딩, 진단 문서 절차
- 대응: 이름 교정 또는 노드 설정의 변환 결과 확인 / 열람 등급 부여 후 재로그인 / 워크스페이스 전환 / 공급자 바인딩 후 재임베딩
- 담당: ws-admin(열람 등급·도구), 플랫폼 admin(공급자·바인딩), 파이프라인 작성자
- 재검증: 같은 질문으로 검색 건수 ≥ 1, 출처에 document_id·chunk_index 표시

### 7-2. 검색과 답변 생성 (4회차 대응)

- Text-to-SQL: ContextGateway → AI Orchestrator(스키마 그래프·용어집·대화 이력, 관련 테이블 10개, 직접 조인 + 다중 홉 조인 경로 힌트 최대 4홉 v1.4+) → SqlGuard(조회문 한 문장, 구문 트리 판정) → 실행. 캐시 히트, 자동 실행 모드 [확인]
- AI Agent Chat(/ai/chat)은 플랫폼 도구를 써서 탐색·SQL 실행·거버넌스 조회·마트 생성·용어 관리를 수행. 도구 수는 AI 기능 개요 46개, 에이전트 채팅 페이지 49개(Tier 1 자동 24 · Tier 2 확인 15 · Tier 3 계획)로 **문서 간 수치가 다름** → 현장 버전에서 확인 [확인, 수치 충돌]. MCP 서버 도구도 39개 실측(2026-08-21)과 Claude Desktop 연동 예시의 33개가 공존 — 호출자 역할·워크스페이스·버전별 차이로 보임 [추정]
- Tier 안전장치: Tier 1(자동) SELECT·카탈로그·품질 점수·용어·문서 검색 / Tier 2(확인 후 실행) 마트 생성·PII 스캔·쿼리 저장·용어 생성·수정·삭제 — 승인하면 리소스가 실제로 만들어지거나 바뀜 / Tier 3(계획만) 커넥터 생성·파이프라인 실행·데이터 삭제 [확인] 에이전트 채팅
- RAG: 벡터 유사도 검색 → LLM 컨텍스트. Hybrid RAG(벡터+그래프+온톨로지)는 ADR-013 [ADR, 구현 범위 확인 필요]
- 답변 실패 원인 분리: "AI만 막힘(화면·SQL은 됨)" → 접근 권한이 아니라 열람 등급 문제 [확인] FAQ
- 출처: 문서 검색 결과에 document_id·chunk_index(v1.4.0+) [확인]

### 7-3. 모델과 에이전트 (5회차 대응)

- 모델 제공자: 외부 LLM/VLM/임베딩 엔드포인트 등록(OpenAI 호환 등), API 키는 Vault에만, 헬스체크, 모델 화이트리스트, 비용 단가. use-case × 워크스페이스 바인딩, 사용량 대시보드(비용·토큰·실패율) [확인]
- ML 허브: 피처 스토어, 노트북(JupyterHub 코드스페이스, CPU 프로필 기본), MLflow 실험·레지스트리, 모델 ABAC(invoke/deploy/manage), 배치 예측, 드리프트. 실시간 서빙은 KServe(클라우드) [확인]

### 7-4. 권한과 보안 (6회차 대응)

- 인증: Keycloak OIDC(realm gend). UI는 PKCE, API는 JWT RS256(JWKS 자동 갱신). 클라이언트 매트릭스 6종(gend-ui·gend-api·trino·oauth2-proxy·jupyterhub·grafana), 인증 패턴 3종(직접 JWT / ForwardAuth(oauth2-proxy) / Native OIDC). Google SSO(운영), 도메인 한정 자동 가입(ADR-0076), 본인 비밀번호 변경(ADR-0090) [확인]
- **고객사 IdP 브로커링(v1.4+)**: 고객이 Okta·Azure AD·사내 Keycloak 등 자체 IdP를 가지면 gend realm에 브로커링해 그 사람 명의의 로컬 계정을 만든다(ADR-0064 D5의 ② 경로). prod Keycloak 변경이라 등록·활성화·회수에 명시 승인 필요. 공공·금융 고객의 "기존 SSO 연계" 요구는 이 절차로 답한다 [확인] 인증 › 고객사 IdP 브로커링
- 보안 등급 기본값 주의: 파싱 노드의 security_level 기본은 PUBLIC, 파이프라인 위저드 기본은 CONFIDENTIAL, 판정 시 NULL은 CONFIDENTIAL. 워크스페이스 상한(max_member_clearance, 미설정 시 CONFIDENTIAL)을 넘는 등급 배포는 전역 관리자만 가능(그 외 422) [확인] 파이프라인 노드
- 역할: admin / analyst / viewer(realm role) + ws-admin(워크스페이스) + 열람 등급(clearance: gend-llm-* 역할 또는 워크스페이스 한정 등급) [확인]
- 2축 모델: L0 워크스페이스(fail-closed) → L1 부서 → L2 Role → L3 ResourceGroup/DataGrant → L4 ABAC(row_filter/column_mask) → clearance(AI) [확인]
- 데이터 액세스 워크플로: 요청(permission_grant) → 검토(승인=발급, ADR-0063) → 부여된 권한(catalog/schema/table). 커넥터 등록 승인은 1회용 [확인]
- 보안 등급 3단계, 대상 3종(카탈로그·테이블·벡터 컬렉션), 미지정 데이터는 CONFIDENTIAL. 새 설치의 tpch·iceberg 등은 등급 행이 없어 테이블 오버라이드로 지정 [확인]
- PII: Presidio 자동 탐지 → 관리자 확인/거부(confirmed_by/at 감사) → 마스킹 뷰. 스캔은 Dagster 센서 큐라 즉시 시작 아님. 활동 로그 4종 [확인]
- 감사: 전체 API 요청 감사(AuditMiddleware → OpenSearch gend-audit*), 감사 체인 검증 알림, 보존 정책 등록(v1.4.2 업그레이드 시 최대 ~11분). 워크스페이스 축 관측은 메트릭 라벨과 감사 로그가 분업(ADR-0033) [확인]
- 네트워크·플랫폼 보안: NetworkPolicy 전면 default-deny(ADR-021), Linkerd mTLS(ADR-022), 클라이언트 IP 신뢰 모델(ADR-0082), gend-api→Trino JWT는 켜지 않음(평문 HTTP 위 토큰은 검사되지 않음, ADR-0080), 출하 OSS는 OSI 승인 라이선스만(ADR-0072), CVE 스캐닝·LDAP/S3 자격증명 회전 문서 [확인]
- 오남용 탐지: 기본 꺼짐(GEND_ABUSE_DETECTION_ENABLED=false) [확인]

**실무 사례 — 같은 질문인데 사용자마다 AI 답이 다르거나 "권한 없음"**
- 원인 후보: 열람 등급 차이(워크스페이스 한정 등급이 전역보다 낮으면 낮은 쪽) / 활성 워크스페이스가 다름 / 테이블 grant 유무 / 행 필터·컬럼 마스크 정책 / 브라우저에 이전 계정의 워크스페이스 선택이 남음(v1.4.2+ 계정별 기억으로 수정)
- 확인 순서: 거부 사유 reason_code(Grant / 네임스페이스 바인딩 / 워크스페이스 선택 / 시스템 카탈로그) → 내 열람 등급 → 데이터 액세스 › 권한 → 접근 정책 → 감사 로그

## 10. 고객 설명과 검수 예시

| 설명 문장 | 시험 조건 | 기대 결과 | 판정 기준 | 증빙 |
|---|---|---|---|---|
| "서로 다른 DB의 표를 한 SQL로 조인해 조회합니다." | 커넥터 2종 이상 등록, 합의한 조인 쿼리 N개 | 결과 반환, 카탈로그 간 조인 성공 | 성공 건수·응답시간 **합의 필요** | 쿼리·결과·실행 시간 캡처 |
| "권한이 없는 행과 열은 보이지 않습니다." | 역할·부서·grant·행 필터·컬럼 마스크를 달리한 계정 2개, 같은 쿼리 | 마스킹·필터 적용 결과 차이 | 노출 0건 **합의 필요** | 계정별 결과 대조표, 감사 로그 |
| "자연어 SQL은 조회만 실행되고, 쓰기 작업은 사용자가 확인 카드를 승인해야만 실행됩니다." | 변경문을 유도하는 자연어 질문 세트(Text-to-SQL) + 마트 생성·용어 생성 요청(에이전트 채팅) | SqlGuard 거부 / Tier 2 확인 카드 표시 후 승인 시에만 실행, Tier 3은 계획만 | 무승인 쓰기 0건 **합의 필요** | 거부 응답·확인 카드 캡처, 감사 로그 |
| "AI가 참조하는 문서는 사용자 열람 등급 안에서만 검색됩니다." | 등급 다른 계정 2개, 같은 질문 | 상위 등급 문서가 하위 계정 출처에 없음 | 노출 0건 | 출처 대조표 |
| "데이터 품질은 4축 점수로 매일 보고됩니다." | 규칙 등록, 예약 스캔 | 점수·등급·이력 표시 | 임계값 **합의 필요** | 품질 대시보드 캡처 |
| "백업은 매일 자동으로 수행되고 복원 절차가 있습니다." | 복원 리허설 1회 | 복원 완료 | RPO/RTO **합의 필요** | 복원 기록, 키 보관 확인서 |
